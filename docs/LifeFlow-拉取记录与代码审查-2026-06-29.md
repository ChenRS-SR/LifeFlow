中间远程新增了约 14 个提交，主要是：

- 复盘系统修复：`97f0991`、`8f73e5c`、`0d0840a`
- 依赖修复：`40852ae`、`96d5a72`

### 1.2 拉取失败的根本原因

远程地址配置为 SSH：

```
origin  git@github.com:ChenRS-SR/LifeFlow.git (fetch)
origin  git@github.com:ChenRS-SR/LifeFlow.git (push)
```

`git fetch` 时报错：

```
kex_exchange_identification: Connection closed by remote host
Connection closed by 198.18.0.39 port 22
fatal: 无法读取远程仓库。
```

排查后发现：

1. `github.com` 在当前环境下被解析到 `198.18.0.39`（这是本地代理/VPN 的地址，不是 GitHub 真实 IP）。
2. SSH 22 端口被该代理直接关闭连接，代理不转发 SSH 流量。
3. HTTPS 流量可以正常走代理（代理作为 HTTP CONNECT 隧道）。

验证命令及结果：

```bash
$ nslookup github.com
Name:   github.com
Address: 198.18.0.39

$ curl -I https://github.com/ChenRS-SR/LifeFlow
HTTP/2 200
```

### 1.3 解决步骤

采用 HTTPS 代替 SSH 进行拉取，步骤如下：

1. **暂存本地未提交改动**
   本地有一个未提交的文件 `docs/服务器部署指南.md`，需要先保护起来，避免拉取时冲突。

   ```bash
   git stash push -m "local: docs/服务器部署指南.md" "docs/服务器部署指南.md"
   ```

2. **切换远程地址为 HTTPS**

   ```bash
   git remote set-url origin https://github.com/ChenRS-SR/LifeFlow.git
   ```

3. **执行拉取**

   ```bash
   git pull origin dev-2.0
   ```

   结果：fast-forward 从 `a5959fd` 更新到 `7fb8c03`，共更新/新增 24 个文件，无冲突。

4. **恢复本地未提交改动**

   ```bash
   git stash pop
   ```

   恢复的 `docs/服务器部署指南.md` 改动与远程变更无冲突，仍保留在工作区。

### 2.3 逐项详细说明

#### 2.3.1 后端路由双轨制（已修复）

**文件：** `backend/app/main.py:13-46`

现在 `main.py` 仅做路由聚合：

```python
from app.api import (
    auth, dashboard, goals, habits, projects, reviews, tasks
)

app.include_router(auth.router, prefix="/api")
app.include_router(dashboard.router, prefix="/api")
app.include_router(goals.router, prefix="/api")
app.include_router(habits.router, prefix="/api")
app.include_router(projects.router, prefix="/api")
app.include_router(reviews.router, prefix="/api")
app.include_router(tasks.router, prefix="/api")
```

`tasks.py`、`habits.py`、`goals.py`、`projects.py` 均使用 `APIRouter(prefix="/tasks")` 等形式，由 main.py 统一挂载。`main.py` 自身不再定义具体端点（健康检查除外）。

#### 2.3.2 任务视图与 `completed_date`（已修复）

**文件：** `backend/app/api/tasks.py:48-144`

当前实现：

- `today`：今日待办（`scheduled_date == today` 或 `due_date == today` 或逾期），排除已完成和垃圾箱。
- `today_completed`：今日已完成（`status == COMPLETED AND completed_date == today`）。
- `week`：采用**方案 B** 语义——计划/截止日期在本周，**或完成日期在本周**的任务。
- `overdue`：`due_date < today` 且未完成、非垃圾箱。
- `completed`：所有已完成任务。

`completed_date` 维护：

- 创建：不设置（任务为 pending）。
- 更新：状态变为 completed 时设为 `date.today()`；非 completed 时清空。
- 完成端点：同上。

#### 2.3.3 习惯打卡 `times_per_day > 1`（已修复）

**文件：** `backend/app/api/habits.py:145-189`

逻辑改为：

- 如果传入 `count`，直接设置。
- 否则：当前次数 `>= target` 时归零（取消），否则 `+1`。

这样 `times_per_day=2` 时需要点 3 次才会取消，避免了之前的“打卡-取消”循环。

#### 2.3.4 项目进度计算（设计保留，建议明确）

**文件：** `backend/app/api/projects.py:62-78`

当前 `project.progress` 只由目标完成率决定：

```python
goals = db.query(models.ProjectGoal).filter(...).all()
progress = (completed / len(goals)) * 100 if goals else 0.0
```

任务完成率不再写入 `project.progress`，而是作为 `total_tasks` / `completed_tasks` 只读字段返回。这不是 bug，但 UI 上「项目完成度」与「项目下任务完成率」可能让用户困惑。建议在项目详情页明确标注「按目标计算」或「按任务计算」。

#### 2.3.5 `is_inbox` 与 `task_type` 同步（已修复）

**文件：** `backend/app/api/tasks.py:262`、`321`

创建和更新时均根据 `task_type == 'inbox'` 同步设置 `is_inbox`。

#### 2.3.6 `user_id` 过滤（大部分已修复，reviews 有遗漏）

核心接口（tasks/habits/goals/projects/dashboard）均已加 `current_user.id` 过滤。

**遗漏：** `backend/app/api/reviews.py:128`、`132`

```python
log = db.query(HabitLog).filter(HabitLog.habit_id == habit.id, HabitLog.date == check_date).first()
logs = db.query(HabitLog).filter(HabitLog.habit_id == habit.id, HabitLog.date >= start_date, HabitLog.date <= end_date).all()
```

这两个查询没有过滤 `HabitLog.user_id`。如果 habit ID 在不同用户间复用（例如自增 ID），可能读取到其他用户的习惯打卡记录。建议修复为：

```python
.filter(HabitLog.habit_id == habit.id, HabitLog.user_id == current_user.id, HabitLog.date == check_date)
```

#### 2.3.7 Dashboard 本周统计（已修复）

**文件：** `backend/app/api/dashboard.py:66-81`

`week_tasks_total` 正确使用了 `week_end`，并且同时考虑 `scheduled_date`、`due_date`、`completed_date` 三个字段。

#### 2.3.8 前端 Week 视图（已修复）

```typescript
useEffect(() => {
  loadData();
}, [currentView, selectedProject?.id, weekOffset]);

// ...

const [tasksRes, projectsRes] = await Promise.all([
```

#### 2.3.9 周视图「逾期」口径不一致（仍存在）

**文件：**

- 前端：`frontend/src/pages/Tasks.tsx:1326-1333`
- 后端：`backend/app/api/tasks.py:94-101`

前端把「逾期」限定为 `due_date < weekStart`（且非今天），目的是让逾期列只显示本周开始之前逾期的任务，本周内的逾期任务显示在对应日期列。

后端 `overdue` 视图是全局的 `due_date < today`。

这是设计上的选择，但如果用户点击侧边栏「已逾期」视图和「本周」视图里的逾期列，会看到不同结果。建议：

- 要么统一口径（都按 `due_date < today`），在周视图里把「今天之前逾期但本周内到期」的任务同时显示在逾期列和日期列；
- 要么在 UI 上明确标注「逾期」的统计范围（如「本周前逾期」）。

## 三、新增代码审查发现的问题

### 3.1 关键问题（建议优先修复）

#### 3.1.1 前端调用 `/api/reviews/today`，后端路由是 `/api/reviews/today/daily`（功能损坏）

**文件：**

- 前端：`frontend/src/services/api.ts:271`
- 后端：`backend/app/api/reviews.py:306`

```typescript
// frontend
getTodayDaily: () => apiClient.get('/api/reviews/today'),

// backend
@router.get("/today/daily", response_model=Optional[schemas.Review])
```

该接口会返回 404，导致「今日复盘」功能无法加载。

**修复建议：** 统一为 `/api/reviews/today/daily` 或 `/api/reviews/today`，前后端保持一致。

#### 3.1.2 `reviews.py` 中 HabitLog 查询缺少 `user_id` 过滤（数据隔离风险）

**文件：** `backend/app/api/reviews.py:128`、`132`

详见 2.3.6。

#### 3.1.3 复盘周期汇总中 Daily 日期计算错误

**文件：** `backend/app/api/reviews.py:72-74`

```python
elif period == "daily":
    start_date = date(year, month or 1, 1)
    end_date = start_date
```

Daily 汇总固定使用每月 1 号，而不是传入的 `date` 参数。应改为使用 `date` 参数解析出的具体日期。

#### 3.1.4 复盘周期汇总使用 `created_at` 而非业务日期

**文件：** `backend/app/api/reviews.py:105-106`、`209-210`

```python
models.Task.created_at >= start_date
models.Task.created_at <= end_date
```

复盘统计按任务创建时间过滤，但任务视图按 `scheduled_date` / `due_date` / `completed_date` 过滤。这会导致「本周复盘」看到的任务和「本周」视图不一致。

**建议：** 复盘统计也应使用 `scheduled_date`、`due_date`、`completed_date` 等业务日期。

### 3.2 中等问题

#### 3.2.1 图片上传缺少大小和格式校验

**文件：** `backend/app/api/reviews.py:401-409`

只检查 `len(image_bytes) == 0`，未限制最大尺寸，也未校验文件魔数（magic bytes）。大图片或恶意请求可能导致内存问题或 AI API 超时。

#### 3.2.2 AI 响应异常处理过宽

**文件：** `backend/app/api/reviews.py:418-419`

```python
except Exception as e:
    raise HTTPException(status_code=500, detail=str(e))
```

捕获所有异常并直接返回错误信息，可能泄露内部信息。

#### 3.2.3 `ai_client.py` 中 API Key 通过 Header 发送

**文件：** `backend/app/services/ai_client.py:83`

虽然这是正常做法，但如果 httpx 开启日志记录，Authorization Header 会明文输出。建议确认生产环境日志级别，避免记录请求头。

#### 3.2.4 Vision 服务硬编码较多

**文件：** `backend/app/services/vision_service.py`

- 图片像素限制硬编码：`min_pixels=3072`，`max_pixels=8388608`
- 餐名、身体部位关键词均为中文硬编码
- AI 调用超时硬编码为 60 秒

建议逐步提取到配置中。

#### 3.2.5 复盘相关 Schema 类型松散

**文件：** `backend/app/schemas/review.py`

```python
timeline: Optional[List[Any]] = None
dimensions: Optional[dict] = None
```

使用 `Any` 和 `dict` 会失去类型校验，建议定义具体的 Pydantic 子模型。

### 3.3 轻微问题

#### 3.3.1 前端 `api.ts` 默认 token

**文件：** `frontend/src/services/api.ts:17`

```typescript
const token = localStorage.getItem('token') || 'token_1';
```

未登录时发送假 token，可能导致后端返回 401 或产生误导。

#### 3.3.2 前端数组索引作为 React key

**文件：** `frontend/src/pages/Reviews.tsx` 多处

使用 `idx` 作为 `key`，列表重排时可能产生渲染问题。

#### 3.3.3 周视图逾期数量显示冗余

**文件：** `frontend/src/pages/Tasks.tsx:1445`

```typescript
{overdueTasks.filter(t => t.status !== 'completed').length}
```

`overdueTasks` 已经在 `1327` 行排除了 completed，此处过滤 redundant。
